> 文档版本：V2.0

> 更新日期：2026-08-27

## 1. 文档说明

### 1.1 编写目的

本文档定义智慧校园学生智能体系统的产品边界、业务流程、功能需求、数据需求、AI 行为约束、非功能需求和验收标准，是后续原型设计、系统设计、开发、测试和验收的统一依据。


### 1.3 需求约定

- `必须`：产品验收不可缺少的能力。
- `应`：正常交付应满足，确有约束时需记录替代方案。
- `可`：增强体验的能力，不得影响必须项交付。
- P0、P1、P2 仅用于实施顺序和风险管理，不代表拆分为多个产品版本。
- 所有需求均属于最终成品范围，变更必须保留原因、影响和验收记录。

## 2. 项目概述

### 2.1 产品定位

系统是一套面向在校学生的智慧校园 AI 助手。学生通过表单或自然语言描述目标，系统结合学生授权数据、食堂数据、考试记录、图书馆馆藏和校园知识库进行检索与分析，生成可解释、可追踪的个性化建议。

### 2.2 建设目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G-01 | 统一学生入口 | 一个账户访问全部四项学生服务 |
| G-02 | 个性化推荐 | 建议能够体现用户约束、偏好和已有数据 |
| G-03 | 结果可解释 | 展示推荐理由、关键依据和必要的资料来源 |
| G-04 | AI 可选择 | 学生可使用基础记录/查询，也可主动启用 AI 分析 |
| G-05 | 安全可信 | 敏感数据经授权使用，低置信度结果明确提示 |
| G-06 | 稳定可扩展 | 满足校园高峰访问、高可用和后续功能扩展需求 |

### 2.3 范围内能力

1. 学生注册或统一身份登录、退出、个人资料、偏好和授权管理。
2. 录入并维护食材、菜品、价格、口味、营养、过敏原和供应状态数据。
3. 根据学生提出的口味、价格、营养、忌口等条件推荐餐食。
4. 使用考试安排记录表维护考试，并可选择启用 AI 学习规划。
5. AI 根据考试难度、剩余时间、掌握情况和可用时间生成复习计划、题目与资料。
6. 保存学校图书馆馆藏数据，根据用户条件推荐校内或未收录书籍。
7. 建设校园资料知识库，通过检索增强生成提供带来源的准确问答。
8. 管理基础数据、知识文档、模型配置、审计日志和系统运行状态。

|---|---|---|
| 学生 | 使用四项核心服务，维护个人记录、偏好和授权 | 仅本人数据及公开校园信息 |
| 食堂数据管理员 | 维护食材、菜品、营养、价格与供应状态 | 食堂业务数据 |
| 图书数据管理员 | 维护图书元数据和馆藏状态 | 图书及馆藏数据 |

| 运维人员 | 部署、监控、告警、备份和恢复 | 运行数据，默认不读取业务正文 |


## 4. 总体业务流程

### 4.1 通用 AI 处理流程

1. 学生登录后选择服务或直接输入自然语言请求。
2. 系统识别意图，加载当前用户、授权范围和业务上下文。
3. 条件不充分时，AI 主动提出少量必要问题；能够从已有数据取得的信息不重复询问。
4. 系统调用受控工具检索业务数据库或知识库。
5. 推荐或回答模块依据约束、适配度和证据生成结果。
6. 页面展示结论、理由、来源、不确定性和可执行的下一步。
7. 系统保存必要的请求摘要、工具调用和结果版本，支持审计与反馈。

### 4.2 关键业务原则

- 业务数据库是菜品、考试、馆藏和校园资料的事实来源，大模型不得编造数据库状态。
- AI 可以分析和建议，不得绕过权限直接修改学生记录或管理数据。
- 影响个人偏好、学习计划或长期记忆的写入必须由学生确认。
- 当数据缺失、冲突或过期时，系统必须说明限制并提供补充信息入口。

### 5.3 学生智能食堂推荐

#### 5.3.1 场景说明

学生可用自然语言或筛选表单提出餐食要求，例如“20 元以内、微辣、高蛋白、不要花生、午餐不要太油”。系统结合已录入的食材、菜品、营养、过敏原、价格和当日供应状态，筛选硬约束并按适配度推荐餐食。

#### 5.3.2 典型流程

1. 学生输入用餐时段、预算、口味、营养目标、忌口或其他要求。
2. 系统读取学生已授权偏好，并对缺失的关键条件进行询问。
3. 系统检索当日可供应菜品及食材信息，先过滤过敏原、忌口、预算上限等硬约束。
4. 系统根据口味、价格、营养、热量、供应和历史反馈计算适配度。
5. 系统返回单品或套餐，展示价格、营养、主要食材、匹配理由和风险提示。
6. 学生可调整条件、比较方案或反馈结果。

#### 5.3.3 详细需求

| 需求编号 | 优先级 | 需求说明 | 验收要点 |
|---|---|---|---|
| FR-FOOD-001 | P0 | 管理员可维护食堂、窗口、菜品名称、图片、价格和供应时段 | 必填校验生效，停供菜品不进入默认推荐 |
| FR-FOOD-002 | P0 | 维护食材、用量、烹饪方式及菜品与食材关系 | 菜品详情可追溯到食材组成 |
| FR-FOOD-003 | P0 | 标注能量、蛋白质、脂肪、碳水、钠等营养信息及数据来源 | 缺失值明确标记，不以模型猜测替代 |
| FR-FOOD-004 | P0 | 标注常见过敏原、忌口标签和特殊饮食标签 | 命中硬性限制时不得作为正常推荐 |

### 5.4 考试安排记录与 AI 学习规划

#### 5.4.1 场景说明

学生先使用考试安排记录表维护近期考试。基础记录功能不依赖 AI；学生可对选定考试主动启用 AI 分析。AI 综合考试难度、剩余时间、掌握情况、每日可用时间、目标和已有资料生成复习安排，并可提供练习题或学习资料。

#### 5.4.2 考试安排记录表

| 字段 | 必填 | 说明 |
|---|---|---|
| 考试名称/科目 | 是 | 学生可识别的考试名称 |
| 考试日期时间 | 是 | 用于计算剩余复习时间 |
| 考试地点 | 否 | 仅用于个人提醒 |
| 考试范围 | 否 | 章节、知识点或资料范围 |
| 难度预估 | 否 | 简单、一般、较难、困难或 1～5 级 |
| 当前掌握情况 | 否 | 总体等级及知识点自评 |
| 目标 | 否 | 目标分数、通过或重点提升项 |
| 每日可用时间 | 否 | 工作日、周末和特定日期可分别填写 |
| 备注 | 否 | 其他限制和说明 |

#### 5.4.3 典型流程

1. 学生创建、编辑或删除近期考试记录，并在日历或列表中查看。
2. 学生选择一个或多个考试，主动点击“AI 分析与生成计划”。
3. 系统读取已填写信息和学生授权的掌握数据、历史计划、错题或资料。
4. 缺少难度、掌握情况、每日可用时间等关键数据时，AI 主动提问。
5. 系统评估优先级、复习工作量和时间冲突，生成可执行计划。
6. 学生确认计划后保存；完成任务或情况变化时可重新规划。
7. 学生可按知识点请求练习题、解析或校内已有资料。

### 5.5 学校书籍查询与 AI 推荐

#### 5.5.1 场景说明

学生可输入主题、用途、专业、关键词、难度、语言、作者或书名等信息。系统结合图书元数据与馆藏状态计算适配度，优先推荐学校图书馆已收录的书籍；若馆藏中没有足够合适的结果，可明确推荐未收录书籍，或同时展示馆藏与馆外两组结果。

#### 5.5.2 典型流程

1. 学生输入书籍名称、作者、ISBN、关键词或自然语言需求。
2. 系统识别主题、用途、难度、语言、版本和馆藏偏好。
3. 系统检索本地图书与馆藏数据库，形成馆藏候选集。
4. 必要时检索允许使用的外部书目数据，形成未收录候选集。
5. 系统按内容适配度、馆藏可用性、难度和版本等因素排序。
6. 页面明确区分“馆藏已有”和“图书馆未收录”，并说明推荐理由。

#### 5.5.3 详细需求

| 需求编号 | 优先级 | 需求说明 | 验收要点 |
|---|---|---|---|
| FR-BOOK-001 | P0 | 管理员维护书名、作者、ISBN、出版社、版本、年份、语言、简介和主题标签 | ISBN 和版本可区分，必填字段校验生效 |
| FR-BOOK-002 | P0 | 维护馆藏位置、索书号、馆藏数量、可用数量和状态 | 推荐详情展示最新馆藏状态与更新时间 |
| FR-BOOK-003 | P0 | 支持书名、作者、ISBN、关键词和主题的组合查询 | 精确条件优先，结果可排序和筛选 |
| FR-BOOK-004 | P0 | AI 从自然语言识别学习主题、用途、难度、语言和版本偏好 | 解析条件可见并允许修正 |
| FR-BOOK-005 | P0 | 信息不足时 AI 可询问用途、基础水平或馆藏偏好 | 已有条件不重复询问 |
| FR-BOOK-006 | P0 | 推荐排序优先考虑内容适配度，在适配度相近时优先馆藏已有且可用的书籍 | 测试数据下排序符合规则 |
| FR-BOOK-007 | P0 | 馆藏没有足够合适结果时可推荐未收录书籍 | 未收录状态醒目标识，不展示虚假索书号 |
| FR-BOOK-008 | P0 | 可同时展示馆藏推荐和未收录推荐，并分别排序 | 两组来源和状态清晰可辨 |
| FR-BOOK-009 | P0 | 每项推荐展示匹配主题、适用人群、难度、版本和推荐理由 | 理由与用户需求相对应 |
| FR-BOOK-010 | P1 | 学生可收藏、隐藏和反馈推荐结果 | 反馈与用户和结果版本关联 |

| FR-BOOK-012 | P0 | 外部书目信息记录来源和获取时间 | 来源不可用时不影响馆藏查询 |

### 5.6 校园知识问答

#### 5.6.1 场景说明

学生可询问学校规章、办事流程、校园服务、活动通知、场所信息等问题。系统从经过审核的校园资料数据库中检索相关片段，基于证据生成准确回答，并展示文档名称、章节、更新时间和原文定位。

#### 5.6.2 典型流程

1. 学生输入问题，系统进行问题规范化和意图识别。
2. 系统按用户权限、文档状态、有效期和适用范围过滤知识。
3. 系统执行关键词与向量混合检索并进行重排序。
4. AI 仅基于检索证据生成回答，展示引用和原文入口。
5. 无充分证据、资料冲突或资料过期时，系统说明情况并建议咨询渠道。
6. 学生可反馈回答错误、无帮助或资料过期。

#### 5.6.3 详细需求

| 需求编号 | 优先级 | 需求说明 | 验收要点 |
|---|---|---|---|
| FR-QA-001 | P0 | 支持 Markdown、TXT、DOCX、PDF 和网页资料导入 | 导入失败可定位文件和原因 |
| FR-QA-002 | P0 | 解析标题、正文、表格和页码并保留原文定位 | 检索片段可回到正确文档位置 |
| FR-QA-003 | P0 | 维护文档类别、责任部门、适用对象、有效期、版本和权限 | 缺少必要元数据不得发布 |
| FR-QA-004 | P0 | 支持草稿、待审核、已发布、已驳回和已失效状态 | 仅已发布且有效资料进入默认检索 |
| FR-QA-005 | P0 | 使用关键词与向量混合检索并支持结果重排序 | 标准问题集检索召回达到验收指标 |
| FR-QA-006 | P0 | 回答前按身份、权限和资料适用范围过滤 | 无权内容不出现在片段、答案和日志明文中 |
| FR-QA-007 | P0 | 事实性回答必须至少包含一个有效引用 | 引用包含文档名、章节/页码和更新时间 |
| FR-QA-008 | P0 | 无充分证据时拒绝编造并说明缺失信息 | 不输出虚构的制度、时间、地点或联系方式 |

## 7. AI 推荐与问答规则

### 7.1 食堂推荐规则

- 硬约束：过敏原、明确忌口、不可供应、学生确认的价格上限。
- 软约束：口味、营养目标、热量偏好、距离、历史反馈和价格偏好。
- 先过滤硬约束，再对候选项评分；评分因素和权重必须可配置、可追踪。
- 无完全匹配时只允许放宽软约束，并明确展示被放宽内容。

### 7.2 学习规划规则

- 输入至少包括考试时间；难度、掌握情况和可用时间不足时应主动询问。
- 任务总时长不得超过学生填写的可用时间，必须预留休息和复盘时间。
- 多场考试按照紧迫度、难度、薄弱程度和目标综合排序，不得只按考试日期排序。
- 计划和练习题必须允许学生修改、拒绝、重新生成和反馈。

### 7.3 图书推荐规则

- 内容适配度是首要排序因素，馆藏可用性用于同等或相近适配度下优先排序。
- 馆藏书和未收录书必须分组或明确标识，不得虚构馆藏数量或位置。
- 未收录推荐必须包含书目信息来源和查询时间。

### 7.4 知识问答规则

- 事实性回答只使用已发布、有效且有权限的知识片段。
- 回答必须引用来源；引用与答案不能相互矛盾。
- 证据不足时回答“暂未查到充分依据”，并给出补充问题或咨询渠道。
- 模型不得把常识、推测或旧会话内容伪装为学校正式规定。

### 8.1 学生端页面

1. 登录页：账号登录、统一认证入口、错误提示和隐私说明。

### 10.2 可用性与容灾

- 核心服务月度可用性目标不低于 99.9%。
- 网关、Java 服务和 Python 服务生产环境至少双副本，故障实例自动摘除。
- 模型不可用时保留登录、考试记录、食堂查询、馆藏查询和关键词检索。
- 关键事务数据 RPO 不超过 5 分钟，RTO 不超过 30 分钟，并定期恢复演练。
- RabbitMQ 任务持久化并支持确认、重试、死信和人工恢复。

### 10.3 安全与隐私

- 外部通信使用 TLS 1.2 及以上；敏感字段、备份和对象存储按策略加密。
- 密码使用强单向哈希，模型和服务密钥不进入代码、页面或日志。
- 所有接口默认拒绝并遵循最小权限，防护 SQL 注入、XSS、CSRF、越权、恶意文件和提示注入。
- 日志不记录密码、令牌、密钥、完整证件信息、过敏明细或未脱敏模型输入。
- 学生可查看授权用途并撤回；敏感导出需额外权限、确认和审计。

| NFR-AIQ-004 | 硬约束安全 | 已确认过敏原、忌口和越权调用违反率为 0 |
| NFR-AIQ-005 | 馆藏真实性 | 推荐中的馆藏位置、数量和状态与数据库一致 |
| NFR-AIQ-006 | 可复现评估 | 记录模型、提示、知识、工具和测试集版本 |

### 10.5 可维护性与可观测性

- 前后端和 Agent 模块边界清晰，遵守仓库 `CONTRIBUTING.md` 的注释与文件规模规范。
- 核心业务规则、权限、推荐过滤和提示模板必须具备自动化测试。
- 指标、日志和链路共享追踪 ID，可定位到模型、检索、工具和数据库。
- 监控可用性、延迟、错误率、队列积压、缓存命中、模型失败、知识命中和成本异常。

## 15. 需求追踪与变更原则

- 每项功能需求必须关联设计项、代码模块、自动化测试和验收结果。
- 需求变更必须记录原因、影响模块、数据迁移、兼容性、测试范围和回滚方式。
- 涉及权限、隐私、推荐硬约束、事实来源和 Agent 工具的变更必须进行安全评审。


## 16. 术语

| 术语 | 定义 |
|---|---|
| Agent/智能体 | 能够理解目标、补充信息、规划步骤并调用受控工具完成任务的软件实体 |
| RAG | 先从受控知识库检索证据，再基于证据生成回答的技术 |
| 硬约束 | 不允许推荐结果违反的条件，例如过敏原、明确忌口和数据权限 |
| 软约束 | 可按优先级权衡的偏好，例如口味、预算偏好和难度偏好 |
| 适配度 | 候选结果与用户需求、数据状态和业务规则的综合匹配程度 |
| 馆藏已有 | 学校图书馆数据库中存在有效馆藏记录的书籍 |
| 未收录 | 当前学校图书馆数据库中不存在有效馆藏记录的书籍 |
| RPO | 故障发生时允许丢失的数据时间范围 |
| RTO | 从故障发生到恢复服务的目标时长 |
