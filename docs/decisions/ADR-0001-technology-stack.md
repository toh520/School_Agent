# ADR-0001：采用 Java 业务后端与 Python Agent 服务的组合架构

- 状态：已接受
- 日期：2026-08-27
- 关联范围：全部功能需求与非功能需求

## 背景

系统是软件工程课设项目，需要在有限时间内完成登录、资料管理、食堂推荐、考试记录与 AI 复习规划、书籍推荐和 RAG 知识问答。技术方案应优先保证团队能够本地开发、测试和课堂演示，同时保持业务规则与 AI 逻辑边界清晰，不按工业级高并发平台进行过度设计。

## 决策

- 前端采用 Vue 3、TypeScript、Vite 和 Element Plus。
- Java 21 + Spring Boot 3.5 负责身份权限、统一资料管理、食堂与食材、简单考试记录、AI 计划书保存、图书馆馆藏和知识元数据等确定性业务。
- Python + FastAPI + LangGraph 负责对话、食堂推荐、学习规划、书籍推荐、RAG 问答、模型调用和 Agent 编排。
- Agent 只能通过经过授权、参数校验和审计的工具接口访问业务能力，不直接修改核心业务表。
- PostgreSQL 为业务事实数据源，pgvector 保存知识向量，开发阶段上传文件保存在受控本地目录。
- 开发和测试默认在个人电脑运行，可选择 Docker Compose 启动 PostgreSQL；课堂展示也以本地环境为主。
- 项目完善后可选择使用 Nginx、Docker Compose 或直接运行 Java/Python 服务部署到个人云服务器，但部署不是课设验收的强制条件。
- 当前不引入 Kubernetes、RabbitMQ、Redis 集群、分布式监控和自动容灾等非必要基础设施。

## 影响

- 优点：业务边界清晰，能够利用 Java 的权限与数据能力和 Python 的 AI 生态，同时保持本地环境可理解、可启动和可演示。
- 代价：存在 Java 与 Python 接口联调成本，需要通过清晰接口、基础日志和自动化测试保证一致性。
- 约束：Python Agent 不得绕过 Java 业务服务修改核心数据；敏感操作必须确认、授权和审计。

## 替代方案

- 全部采用 Python：AI 开发简单，但团队既定 Java 技术栈、登录权限和业务数据层需要重新调整。
- 全部采用 Java：业务治理统一，但 Agent/RAG 生态接入和实验效率较低。
- 工业级微服务与 Kubernetes：扩展能力强，但明显超过课设范围，会增加部署、运维和排错成本，因此当前不采用。
