# 智慧校园智能体系统技术开发报告

> 文档版本：V1.0  
> 编制日期：2026-08-28  
> 需求基线：`智慧校园智能体系统需求分析报告 V1.0`  
> 适用范围：系统设计、迭代开发、代码审查、测试与项目验收

## 1. 文档目的

本文档将已确认的需求转化为可执行的技术模块和开发阶段，明确各模块职责、接口边界、阶段交付物、审查点和退出条件。团队应以需求编号、Issue、代码、测试和验收证据之间的可追踪关系推进开发。

本项目是软件工程课设，技术方案以本地可运行、核心流程完整、数据安全、AI 结果可信和课堂演示稳定为优先目标，不引入超出实际需要的复杂基础设施。

## 2. 技术目标与设计原则

### 2.1 技术目标

1. 建立统一登录、权限、授权和审计能力，为全部业务模块提供安全基础。
2. 完成智能食堂、考试记录与学习规划、书籍查询推荐、校园知识问答四项学生服务。
3. 建立统一信息资料管理后台，保证食堂、图书和知识数据可维护、可校验、可追踪。
4. 将确定性业务规则与大模型生成能力分离，确保模型不可用时基础业务仍可使用。
5. 形成需求、设计、代码、测试和验收证据闭环，支持团队协作和最终答辩。

### 2.2 设计原则

- PostgreSQL 是业务事实数据源，AI 不得猜测或覆盖事实字段。
- Java 服务负责身份权限、业务数据、确定性规则和写入控制；Python 服务负责对话、检索、推荐和 Agent 编排。
- Agent 只通过受控工具接口访问业务能力，不直接修改核心业务表。
- 所有个人数据按用户隔离；敏感信息必须先授权、后使用，并记录审计事件。
- 推荐先执行硬约束过滤，再执行软约束评分；任何降级不得放宽安全和权限约束。
- AI 输出必须呈现依据、来源、关键假设和不确定性。
- 每个阶段必须满足退出条件后才能进入下一阶段；涉及跨模块依赖时可并行开发，但不得绕过接口评审。

## 3. 总体技术架构

```text
学生端 / 信息资料管理端（Vue 3 + TypeScript）
                    │ HTTP JSON / SSE
                    ▼
      Java 核心业务服务（Spring Boot）
  认证授权、资料管理、业务数据、审计、受控工具
          │                      │
          │ REST                 │ SQL
          ▼                      ▼
 Python Agent 服务          PostgreSQL + pgvector
意图识别、推荐、规划、RAG      事实数据、向量、调用轨迹
          │
          ▼
     大模型适配层 / Embedding 服务
```

### 3.1 运行边界

| 层级 | 技术 | 核心责任 | 禁止事项 |
|---|---|---|---|
| Web 前端 | Vue 3、TypeScript、Vite、Element Plus、Pinia | 页面、表单、状态、错误反馈、SSE 展示 | 不在前端实现可信权限判断或保存密钥 |
| Java 业务服务 | Java 21、Spring Boot 3.5、Spring Security、MyBatis-Plus | 认证、授权、事务、业务数据、后台、审计、工具接口 | 不把核心业务校验交给前端或模型 |
| Python Agent | Python 3.11/3.12、FastAPI、LangGraph | 对话、意图、条件提取、推荐编排、学习规划、RAG | 不直连核心表执行写入，不绕过授权 |
| 数据层 | PostgreSQL、pgvector、本地受控文件目录 | 事实数据、关系数据、向量、文件元数据 | 不保存明文密码、令牌或未脱敏敏感日志 |
| 测试层 | JUnit、pytest、Playwright、接口测试 | 单元、集成、契约、端到端和验收测试 | 不仅依赖人工演示判断完成状态 |

### 4.2 M01 工程基础与公共规范

建议目录：

```text
School_Agent/
├─ apps/
│  └─ web/                  # 学生端与统一管理端
├─ services/
│  ├─ core-service/         # Java 核心业务服务
│  └─ agent-service/        # Python Agent 服务
├─ deploy/                  # Docker Compose、Nginx 和环境示例
├─ docs/                    # 需求、设计、决策和过程证据
├─ tests/                   # 跨服务契约、E2E、性能和安全测试
└─ tools/                   # 环境检查、数据初始化和文档校验
```

关键设计内容：统一环境变量命名、配置分层、数据库迁移规则、响应结构、错误码、时间与时区、分页结构、请求标识、日志字段、文件上传限制和健康检查。

### 4.3 M02 身份、用户与授权

子模块包括认证会话、学生资料、个人偏好、敏感数据授权、访问控制、数据撤回与清理、认证与权限审计。所有按用户访问的查询必须在服务端绑定当前用户身份，禁止仅依赖请求中的 `userId`。

### 4.4 M03 统一信息资料管理

统一后台使用同一管理员角色和导航，按资料类型提供食堂与食材、图书与馆藏、知识文档、账号及必要配置页面。导入流程至少包含预校验、重复检测、完整度提示、确认入库、错误清单和操作日志。

### 4.5 M04 通用 Agent 平台

核心流程为“识别意图—加载已授权上下文—补充必要条件—调用受控工具—生成结构化结果—展示证据与限制—保存轨迹与反馈”。工具必须定义输入 Schema、权限范围、超时、错误类型和是否允许写入；任何写入类动作均需由 Java 服务重新校验并在必要时要求用户确认。

### 4.6 M05 智能食堂

确定性规则放在可测试的领域服务中：先过滤过敏原、明确忌口、停供和硬预算，再根据口味、价格、营养、可用性与反馈计算分数。AI 负责自然语言条件提取和解释，不负责决定是否绕过硬约束。

### 4.7 M06 考试与学习规划

基础考试记录必须完全不依赖 AI。学习规划只在学生主动触发后运行，计划总时长不得超过可用时间，并应说明优先级、假设和信息不足。计划书保存前由业务服务验证所有权和数据结构。

### 4.8 M07 图书与馆藏推荐

本地馆藏是库存状态的唯一事实来源。内容适配度优先，在适配度相近时优先已馆藏且可用的书籍。馆外结果必须明确标识“未收录”，记录来源和查询时间，且不得生成虚假索书号、馆藏数量或位置。

### 4.9 M08 校园知识问答

知识资料遵循草稿、待审核、已发布、已驳回、已失效状态流转。检索前按身份、资料状态、有效期和适用范围过滤；回答只能基于有效证据。事实性答案至少包含一个可定位引用，证据不足时拒绝编造。

### 4.10 M09 审计、质量与可观测性

日志至少关联请求标识、用户匿名标识、模块、事件、结果、耗时和错误类型。模型调用应记录模型版本、提示模板版本、知识版本、工具名和结果版本，但不得记录密码、令牌、密钥、完整敏感信息或未脱敏对话正文。

### 4.11 M10 测试、演示与部署

测试模块统一管理跨服务契约、端到端验收、安全、性能和 AI 质量用例；演示与部署模块维护环境检查、脱敏初始化数据、备份恢复、启动顺序和故障降级说明。所有验收证据应记录执行环境、数据版本、操作步骤、实际结果和责任人。

## 5. 开发阶段与里程碑

建议采用从阶段 0 到阶段 8 的 9 个阶段推进。阶段可按团队人数适当重叠，但每个阶段的审查结论必须记录在项目日志或 Pull Request 中。

### 阶段 0：需求基线确认与开发准备

**目标**：确保团队对范围、优先级、验收方式和协作规则理解一致。

**主要任务**：

- 冻结 V1.0 需求基线，建立需求到验收场景的映射。
- 为 M01～M10 创建 Epic/Issue，指定负责人和依赖关系。
- 确认本地开发所需 Node.js、JDK、Python、PostgreSQL 版本。
- 补充接口、数据库、安全和 AI 评估相关 ADR。
- 确定脱敏演示数据来源，不使用真实敏感个人信息。

**交付物**：需求基线、任务看板、初始追踪矩阵、开发环境清单、风险清单、ADR 列表。

**阶段审查点**：

- [ ] 所有 P0 需求均已分配模块，未出现遗漏或重复归属。
- [ ] 需求中的术语、角色、数据范围和验收口径无明显冲突。
- [ ] 四项核心业务、统一后台、授权、审计和降级均进入计划。
- [ ] 每项任务具备需求编号、完成定义、依赖和负责人。
- [ ] 敏感数据、外部模型和外部书目来源的使用边界已明确。
- [ ] 技术选择与 ADR-0001 一致；变更已有新 ADR 记录。

**退出条件**：P0 需求覆盖率达到 100%，关键风险有责任人和应对措施，团队能够按统一说明准备环境。

### 阶段 1：架构设计、接口契约与数据设计

**目标**：在编码前稳定跨服务边界，降低前后端及 Java/Python 联调返工。

**主要任务**：

- 输出模块组件图、调用链和关键时序图。
- 设计用户、食堂、考试、图书、知识、对话、工具调用和审计数据模型。
- 定义 `/api/*`、`/internal/tools` 和 SSE 的接口契约及错误码。
- 定义授权校验、工具白名单、文件处理、知识状态流转和降级策略。
- 设计数据库迁移、初始化数据和备份恢复方案。

**交付物**：总体设计、ER 图、数据字典、OpenAPI/接口说明、工具 Schema、安全设计、相关 ADR。

**阶段审查点**：

- [ ] 每个事实字段均有唯一权威来源，AI 生成字段与事实字段分离。
- [ ] 表主键、唯一约束、外键、索引、逻辑删除和时间字段设计合理。
- [ ] 个人数据查询在接口层和数据层均能实施用户隔离。
- [ ] 接口包含正常、参数错误、未认证、无权限、冲突、超时和降级响应。
- [ ] Java/Python 数据结构、枚举、时区、分页和错误语义一致。
- [ ] `/internal/tools` 定义身份透传、授权、超时、审计和幂等要求。
- [ ] 文件上传限制类型、大小、存储路径、恶意文件防护和失败清理。
- [ ] 数据迁移支持升级和可验证回退，初始化数据不含真实敏感信息。

**退出条件**：核心接口和数据模型通过团队评审；前端、Java 和 Python 可基于契约独立开发；高风险设计项已有 ADR。

### 阶段 2：工程骨架与公共基础能力

**目标**：建立可启动、可测试、可观察的最小端到端骨架。

**主要任务**：

- 创建 Vue、Spring Boot 和 FastAPI 工程及统一配置样例。
- 建立 PostgreSQL/pgvector、迁移脚本和脱敏初始化数据。
- 实现统一响应、错误处理、请求标识、日志脱敏和健康检查。
- 建立测试框架、静态检查、格式化和基本构建流程。
- 打通浏览器—Java—Python—数据库的健康链路。

**交付物**：三端工程骨架、数据库迁移、环境模板、启动说明、冒烟测试和健康检查。

**阶段审查点**：

- [ ] 新成员可仅根据 README 在本地启动全部必要服务。
- [ ] 密钥仅通过环境配置提供，仓库和日志中不存在真实密钥。
- [ ] 配置缺失时服务快速失败并给出可理解错误，不静默使用危险默认值。
- [ ] 请求可通过统一标识跨前端、Java 和 Python 定位。
- [ ] 数据库迁移可在空库重复执行，初始化数据可重建。
- [ ] Java、Python 和前端至少各有一个自动化冒烟测试。
- [ ] 依赖版本已固定，生成物、虚拟环境和密钥文件已正确忽略。

**退出条件**：最小链路自动化冒烟测试通过，另一名成员可复现启动，基础日志能定位一次跨服务请求。

### 阶段 3：身份权限、授权与统一资料后台

**目标**：先建立所有业务模块共同依赖的安全和数据维护能力。

**主要任务**：

- 实现账号密码登录、令牌刷新、退出和会话过期。
- 实现学生资料、偏好、授权、撤回和允许删除的数据清理。
- 实现学生/信息资料管理员角色及默认拒绝策略。
- 实现统一后台导航、基础 CRUD、校验、完整度提示和操作日志。
- 建立食堂、书目、馆藏、知识文档的最小可用管理页面。

**交付物**：认证授权模块、个人中心、统一后台、数据维护接口、权限测试和审计记录。

**阶段审查点**：

- [ ] 无效登录、过期令牌、退出令牌和刷新流程行为符合预期。
- [ ] 修改请求中的用户编号不能访问或修改其他学生数据。
- [ ] 管理员不能查看未授权的学生私密对话正文。
- [ ] 敏感授权按用途分别保存，默认未授权，撤回后新请求立即停止使用。
- [ ] 密码使用强单向哈希，令牌、密码和敏感字段未写入日志。
- [ ] 后台必填、格式、重复、引用关系和乐观并发校验有效。
- [ ] 重要登录、权限变化、敏感访问和管理操作均生成审计事件。
- [ ] AT-01 和 AT-15 已形成自动化或可重复人工验收记录。

**退出条件**：身份与数据隔离测试通过；S1/S2 权限缺陷为 0；业务模块具备可使用的脱敏测试数据。

### 阶段 4：确定性核心业务开发

**目标**：不依赖大模型完成四项服务的事实数据、基础查询和规则能力。

**主要任务**：

- 食堂：菜品、食材、营养、过敏原、供应、硬约束过滤和规则评分。
- 考试：科目/时间/备注 CRUD、按时间排序、最近考试和剩余时间。
- 图书：书目、馆藏、组合查询、馆藏状态和更新时间。
- 知识：文档元数据、状态流转、导入、解析、分块和关键词检索。
- 为 Agent 提供只读或受控写入的内部工具接口。

**交付物**：四域业务接口与页面、规则服务、内部工具接口、单元/集成测试、示例数据。

**阶段审查点**：

- [ ] 模型服务关闭后，登录、考试记录、食堂查询、馆藏查询和关键词检索仍可用。
- [ ] 过敏原、忌口、停供和硬预算过滤由确定性代码实施，违反率为 0。
- [ ] 考试排序、过期判断和剩余时间在统一时区下边界正确。
- [ ] 馆藏位置、数量、状态和更新时间全部来自数据库。
- [ ] 只有已发布、有效且有权限的知识进入默认检索。
- [ ] 工具接口执行参数、身份、权限、超时和结果大小校验。
- [ ] 并发更新、重复提交、事务失败不会产生半条或矛盾数据。
- [ ] 核心规则具备正常、边界、异常和越权测试。

**退出条件**：AT-02、AT-03、AT-05、AT-10 的非 AI 部分通过；基础业务在无模型环境下稳定运行。

### 阶段 5：通用 Agent、推荐、规划与 RAG

**目标**：在可靠业务工具之上实现受控、可解释、可降级的 AI 能力。

**主要任务**：

- 实现多轮对话、四类意图识别、授权上下文加载和必要追问。
- 定义工具注册、调用校验、超时、重试、降级和调用轨迹。
- 实现自然语言条件提取，并允许用户查看和修正。
- 实现食堂推荐解释、考试复习计划、图书推荐和 RAG 问答。
- 实现 SSE 状态与流式内容、反馈和结果版本管理。
- 建立固定测试集和模型/提示/知识版本记录。

**交付物**：Agent 工作流、提示模板、工具适配层、AI 页面交互、结构化结果、质量评估报告。

**阶段审查点**：

- [ ] 未经学生主动触发，考试记录页面不调用 AI。
- [ ] Agent 只使用已授权数据，工具调用前后均保留权限校验。
- [ ] 已有信息不重复询问；追问仅针对影响结果的必要字段且有次数上限。
- [ ] 解析条件以标签或表单展示，用户修正后实际使用修正值。
- [ ] 学习计划总时长不超过可用时间，并包含休息、复盘、假设和限制。
- [ ] 书籍结果清晰区分馆藏与未收录，馆外信息含来源和时间。
- [ ] 校园事实性回答有效引用覆盖率达到 100%，证据不足时拒答。
- [ ] 提示注入不能绕过权限、工具白名单、数据范围或知识状态过滤。
- [ ] 模型、工具、网络异常可降级，失败不会造成错误写入或数据丢失。
- [ ] 标准集条件识别准确率不低于 90%，正常依赖下工具成功率不低于 95%。

**退出条件**：AT-02～14 和 AT-16 的主要路径通过；AI 硬约束违反率为 0；结果具有可复查的证据和版本。

### 阶段 6：前端集成、体验完善与跨模块联调

**目标**：形成完整、连贯、可理解的学生端和统一管理端体验。

**主要任务**：

- 完成首页、智能食堂、考试安排、书籍查询、知识问答和个人中心。
- 完成后台资料维护、导入、审核、完整度和错误清单交互。
- 统一加载、空状态、错误、重试、降级、确认和成功反馈。
- 完成响应式布局、键盘可用性、防重复提交和未保存离开提示。
- 打通收藏、反馈、历史、引用原文和结果重新生成。

**交付物**：端到端功能界面、交互规范、跨服务联调记录、浏览器兼容与可用性检查结果。

**阶段审查点**：

- [ ] 所有核心页面均覆盖加载、空数据、成功、权限不足、服务异常和降级状态。
- [ ] SSE 中断后可安全重试，不重复写入计划或结果记录。
- [ ] 关键表单即时校验，提交期间禁用重复操作，离开前提示未保存内容。
- [ ] 引用能够打开正确文档位置；失效或无权来源不可访问。
- [ ] 桌面端和主流移动浏览器可用，窄屏核心内容无横向溢出。
- [ ] 颜色不是状态的唯一表达方式，关键操作支持键盘完成。
- [ ] 权限或模型错误不暴露堆栈、内部地址、提示词或敏感数据。
- [ ] 四项核心流程由非开发者按验收脚本成功操作至少一次。

**退出条件**：全部 P0 页面完成，端到端主路径稳定，跨模块 S1/S2 缺陷为 0。

### 阶段 7：系统测试、安全审查与性能优化

**目标**：以需求和风险为依据完成系统级验证，达到验收候选状态。

**主要任务**：

- 执行单元、集成、契约、端到端、权限、安全、AI 质量和恢复测试。
- 覆盖 SQL 注入、XSS、CSRF、越权、恶意文件、提示注入和敏感日志检查。
- 验证页面、普通查询、AI 首次反馈和课堂并发体验指标。
- 执行备份、恢复、重启、模型中断和数据库异常演练。
- 更新追踪矩阵、测试日志、缺陷清单和验收证据。

**交付物**：测试报告、安全审查记录、性能结果、AI 评估结果、缺陷清单、追踪矩阵。

**阶段审查点**：

- [ ] 每项 P0 需求至少关联一个自动化测试或明确的人工验收用例。
- [ ] AT-01～18 均有结果、执行时间、环境、证据和责任人。
- [ ] S1、S2 缺陷为 0；S3 有负责人、计划和不影响验收的说明。
- [ ] 权限绕过、敏感日志、提示注入和恶意文件场景已验证。
- [ ] 主要页面可见加载、普通查询和 AI 首次反馈满足 NFR 指标。
- [ ] 过敏原/忌口违反率为 0，馆藏真实性一致，问答引用覆盖率为 100%。
- [ ] 模型、提示、知识、工具和测试集版本可复现。
- [ ] 应用重启后数据仍存在，备份或初始化脚本可恢复演示环境。

**退出条件**：达到需求报告缺陷退出准则，追踪矩阵无未解释空项，形成可发布候选版本。

### 阶段 8：验收、演示与项目收尾

**目标**：完成课堂演示、材料归档和可维护交付。

**主要任务**：

- 冻结演示版本、数据库和模型/提示配置。
- 准备正常流程、异常降级和安全边界三类演示脚本。
- 在实际演示电脑执行全新启动、连续操作和恢复演练。
- 整理技术报告、用户说明、测试证据、ADR、会议纪要和项目日志。
- 对遗留问题、限制和后续扩展形成维护清单。

**交付物**：验收版本、演示数据、启动/恢复手册、演示脚本、验收报告、归档材料。

**阶段审查点**：

- [ ] 按 README 在演示电脑从零启动成功，端口和依赖冲突有处理说明。
- [ ] 演示数据完整、脱敏、可重复导入，且不依赖临时手工修库。
- [ ] 网络或模型不可用时有可展示的降级路径。
- [ ] 演示账号权限正确，密钥和后台敏感配置不会出现在投屏画面。
- [ ] 演示脚本覆盖四项核心服务、统一后台、授权撤回和引用证据。
- [ ] 需求追踪矩阵、测试日志、项目日志和 ADR 已更新至最终状态。
- [ ] 已知限制明确记录，不把未完成能力描述为已完成。
- [ ] 项目源码、数据库迁移、初始化数据和文档均已备份。

**退出条件**：AT-01～18 完成验收，最终缺陷满足退出准则，交付物可由非原开发者复现。

## 6. 模块并行开发建议

完成阶段 2 和阶段 3 的公共依赖后，可按以下工作流并行推进：

| 工作流 | 负责范围 | 必须共享的契约 |
|---|---|---|
| A：前端与体验 | 学生端、后台、SSE 展示、统一状态 | OpenAPI、错误码、权限状态、结构化结果 Schema |
| B：Java 业务 | IAM、后台、食堂、考试、图书、工具接口 | 数据字典、事务边界、工具 Schema、审计字段 |
| C：Python Agent | 对话、推荐、规划、RAG、模型适配 | 工具 Schema、授权上下文、结果 Schema、超时策略 |
| D：测试与质量 | 契约、E2E、安全、性能、AI 评估 | 验收场景、测试数据、版本标识、证据格式 |

合并顺序建议为“契约与测试数据—后端能力—Agent 编排—前端集成—端到端测试”。契约发生不兼容变更时，必须先更新设计与契约测试，再修改调用方。

## 7. 通用代码审查清单

每个 Pull Request 除阶段专属审查点外，至少检查以下内容：

### 7.1 需求与范围

- [ ] PR 关联需求编号、Issue 和明确的完成定义。
- [ ] 改动只覆盖声明范围；非目标变更已拆分或解释。
- [ ] 需求、接口、数据或权限发生变化时已同步更新文档和追踪矩阵。

### 7.2 设计与代码质量

- [ ] 模块职责清晰，无跨层绕过或重复实现核心规则。
- [ ] 公共接口、复杂算法、安全边界和失败策略有必要说明。
- [ ] 无无理由的超长文件、超长函数、深层嵌套或大段复制代码。
- [ ] 异常被正确分类、转换和记录，不吞掉错误或暴露内部细节。

### 7.3 数据与兼容性

- [ ] 数据迁移兼容已有数据，约束和索引与访问方式匹配。
- [ ] 写操作具备事务、幂等或重复提交保护。
- [ ] 删除、撤回和失败清理行为符合数据保护要求。
- [ ] API 变更已评估前端、Java、Python 和测试的兼容性。

### 7.4 安全与 AI 边界

- [ ] 服务端执行身份、角色、资源所有权和数据授权校验。
- [ ] 输入、上传文件、模型输出和外部数据均视为不可信内容。
- [ ] 密钥、令牌、密码和敏感个人信息未进入代码、响应或日志。
- [ ] Agent 未绕过工具接口；AI 输出未直接覆盖事实数据。
- [ ] 硬约束、知识权限、引用和拒答逻辑有自动化测试。

### 7.5 验证与证据

- [ ] 新增或修改逻辑包含正常、边界、异常和权限测试。
- [ ] PR 列出实际执行的命令、结果和必要截图。
- [ ] 测试数据可重复且已脱敏，不依赖作者机器的隐式状态。
- [ ] 至少一名非作者成员完成评审，所有阻断意见已处理。

## 8. 阶段质量门禁

| 门禁 | 判断标准 | 未通过处理 |
|---|---|---|
| G1 需求覆盖 | P0 需求全部映射到模块、任务和验收场景 | 不进入架构编码 |
| G2 设计稳定 | 核心数据、接口、权限和工具契约评审通过 | 不开展跨服务并行实现 |
| G3 基础可运行 | 新环境可启动，冒烟测试和日志链路通过 | 不合并大规模业务功能 |
| G4 安全基础 | 登录、用户隔离、授权和审计通过 | 不开放 AI 使用个人数据 |
| G5 业务可信 | 无模型时基础功能可用，事实与硬约束测试通过 | 不接入生成式推荐结果 |
| G6 AI 可控 | 引用、拒答、工具权限、降级和质量指标通过 | 不进入完整演示联调 |
| G7 发布候选 | S1/S2 为 0，AT-01～18 有证据，恢复演练通过 | 不冻结验收版本 |

## 9. 需求追踪与过程留痕

每项需求至少维护以下链路：

```text
需求编号 → Issue/任务 → 设计或 ADR → 实现路径/PR
        → 自动化测试 → 人工验收记录 → 最终状态
```

状态统一使用：`待设计`、`开发中`、`待验收`、`已验收`、`受阻`。完成开发或变更合并后，应同步更新：

- `docs/process/TRACEABILITY_MATRIX.md`
- `docs/process/PROJECT_LOG.md`
- `docs/process/TEST_LOG.md`
- 受影响的需求、设计、接口或 ADR 文档

## 10. 风险驱动的重点复审项

| 风险 | 高风险位置 | 必须复审的证据 |
|---|---|---|
| 过敏或忌口误推荐 | 食堂过滤、条件解析、套餐合计、降级 | 硬约束单元测试、端到端反例、结果快照 |
| 学生数据越权 | 所有按用户查询、导出、历史记录和工具 | 双用户越权测试、审计事件、日志脱敏检查 |
| AI 编造校园规定 | 知识过滤、检索、提示、引用和拒答 | 标准问答集、无证据/冲突测试、引用定位 |
| 虚构馆藏状态 | 推荐合并、缓存、馆外数据和展示 | 数据库对账、馆藏/未收录分组测试 |
| 学习计划不可执行 | 时间计算、多考试优先级、信息缺失 | 总时长校验、边界日期和多考试用例 |
| 工具误用或提示注入 | Agent 路由、工具参数、身份透传 | 非法工具、越权参数、注入攻击测试 |
| 演示环境不稳定 | 依赖、模型网络、初始化与备份 | 全新启动、断网降级、重启和恢复记录 |

## 11. 完成定义（Definition of Done）

一个需求或阶段仅在以下条件全部满足时视为完成：

1. 需求验收标准已实现，未通过改变口径规避原需求。
2. 代码已合并到稳定分支，至少一名非作者完成评审。
3. 自动化测试通过，必要人工验收已记录环境、步骤、结果和证据。
4. 权限、隐私、日志、错误处理、AI 边界和降级路径已检查。
5. 数据迁移、接口兼容和失败恢复已按改动风险验证。
6. README、设计文档、ADR、项目日志和追踪矩阵已同步更新。
7. 不存在 S1/S2 缺陷；S3 缺陷有明确责任人和处理计划。
8. 功能能在团队约定的本地环境复现，并可纳入最终课堂演示。

## 12. 变更控制

需求、架构、数据库、公共接口、权限模型、Agent 工具或验收指标发生变化时，变更提交必须说明：变更原因、影响模块、兼容性、数据迁移、测试范围、回滚方式和文档更新位置。涉及个人信息、推荐硬约束、事实来源、提示注入防护或工具写入权限的变更，应由至少一名非作者进行专项安全复审。
